# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A small Python data-munging pipeline that joins Zillow home-value data with FRED income data (per-capita, and median household income via Census SAIPE) at the US county level, producing a single tidy CSV (one row per county-month) suitable for downstream visualization (e.g. price-to-income ratios over time, on either income basis). The code is intentionally simplistic ("definitely contains inaccuracies" per the README) — favor small, direct fixes over refactoring.

## Setup

```
pip install -r requirements.txt
```

Dependencies: `requests`, `pandas`.

## Pipeline / commands

There is no build/lint/test tooling — this is a data pipeline run manually, in order:

1. **`fred_fetch.py`** — fetches per-capita personal income data from FRED (release 175, one element per state) into `data/fred/<State>-<year>-01-01.json`. Reads the API key from `fred_key.txt` (gitignored, not committed — see `# UPDATE:` comment). Flags: `--start-year`/`--end-year` to bound the range, `--force` to re-fetch and overwrite years that already have a file (useful for checking whether a previously-blank/unpublished year has since been released — BEA's county personal income release lags roughly a year, so a given year is often blank on first fetch and populated later), `--limit` to cap the number of requests for a quick test. Sleeps 2s between requests, matching `fred.stlouisfed.org`'s declared `Crawl-delay: 2` (stricter than this repo's 1 req/sec policy floor, so the stricter one wins).
2. **`fred_household_fetch.py`** — fetches county-level median household income (Census SAIPE, mirrored by FRED as release 346) into `data/fred_household/<fips>.json`. A structurally different fetch than `fred_fetch.py`: SAIPE has one series per county, with FIPS embedded directly in the series id (`MHI<state_abbr><fips5>A052NCEN`) rather than release 175's one-table-per-state-per-year — so this needs no NRCS name-matching crosswalk (it only reads `data/nrcs/nrcs_fips_codes.csv` for the `(fips, state_abbr)` pairs to build series ids from), and one request per county fetches that county's *entire* history in one call rather than one request per state-year. `--start-year` (default 2000, per this project's needs) bounds how far back is requested; `--force`/`--limit` behave like `fred_fetch.py`. Same 2s delay, same host. Skips territory FIPS prefixes (`NON_SAIPE_FIPS_PREFIXES` — American Samoa, Guam, Northern Mariana Islands, Puerto Rico, US Virgin Islands) upfront, since SAIPE only covers the 50 states + DC and every one of those would otherwise 400 ("The series does not exist") on every run — a real, permanent SAIPE coverage gap, not a crosswalk or fetch bug. Writes each file via a temp-file-then-`os.replace()` and catches per-request network/JSON errors (logs and continues) so a ~1.8-hour unattended run over ~3,170 counties survives a flaky request instead of dying, and a kill mid-write can't leave a half-written file that the skip-existing check above would then treat as "already fetched" forever.
3. **`fred_household_growth_fetch.py`** — fetches state- and national-level *real median household income* (FRED release 249, `MEHOINUS<state_abbr>A672N` / `MEHOINUSA672N`) into `data/fred_household_growth/<abbr>.json` (`US.json` for national). Not used for output directly — `build_income.py` uses its year-over-year growth rate to extrapolate SAIPE into years it hasn't published yet, the household-income equivalent of the QCEW-rate extrapolation described below (see step 4). Only ~51 series total, so no `--limit`/`--states` narrowing; `--force`/`--start-year` behave like the other fetch scripts.
4. Manually download county-level Zillow data (e.g. ZHVI All Homes, Smoothed/Seasonally Adjusted) from https://www.zillow.com/research/data/ and place it at `data/zillow/<home-type>/<filename>` — one subfolder per home-value series, e.g. `data/zillow/all-homes/` and `data/zillow/single-family-homes/` — then update the `zillow_paths` dict (`# UPDATE:`) in `create_output.py` and `web_data_build.py` to match. Both scripts key on a `home_type` tag (`all_homes`, `single_family`, ...) per entry: `create_output.py` stacks all configured home types into `outputs/fips_zillow_income.csv` as extra rows (one row per county-month-home_type, distinguished by the `home_type` column), and `web_data_build.py` ships one ZHVI matrix per home_type in `dataset.json` (see its Web visualization entry below) so the client can switch between them. Zillow's county **rent** series (ZORI, Zillow Observed Rent Index — typical monthly asking rent, `data/zillow/rentals-all-homes/`) is configured separately, as `zillow_rent_path` in both scripts, not as a `zillow_paths` entry: it's $/mo rent, not a home value, so the home-type toggle and price/income ratio don't apply to it. Coverage is much thinner than ZHVI's (~1,400 counties vs. ~3,070, series starting 2015 at the earliest, many only in the last year), and it's smoothed but not seasonally adjusted.
5. **`build_income.py`** — flattens both FRED-sourced income measures into one fips-keyed, monthly table:
   - **Per-capita income**: attaches FIPS to the `fred_fetch.py` JSON via `data/nrcs/nrcs_fips_codes.csv` (matched on state abbr + county name, not a hand-built crosswalk — see Architecture notes). For years beyond FRED's own coverage (currently 2025+), extrapolates each county's last real figure forward using a growth *rate* taken from QCEW's real average-weekly-wage data (`data/qcew/`) — county-level rate if QCEW has that county both years, else state-level, else national — tagged `income_source = fred_estimated_{county,state,national}_qcew_rate`. This is a rate transfer, not splicing QCEW income levels into FRED's series (see QCEW section below for why mixing levels would be a methodology break; a rate multiplier avoids that).
   - **Household income**: reads `fred_household_fetch.py`'s per-county SAIPE JSON directly (FIPS comes from the filename — no crosswalk needed). For years beyond SAIPE's coverage, extrapolates using the state (else national) growth rate from `fred_household_growth_fetch.py`'s real-median-household-income series (`data/fred_household_growth/`) — tagged `household_income_source = saipe_estimated_{state,national}_acs_rate`. Because that series comes from the same underlying survey as SAIPE (CPS ASEC), it can lag just as far behind — e.g. both currently cap at 2024 since the "Income in the United States: 2025" release hasn't happened yet — so for years beyond *its* coverage too, there's a second fallback tier to QCEW's real average-weekly-wage rate (county, else state, else national — `data/qcew/`), the same proxy and same rate-transfer-not-level-splice reasoning as per-capita income's QCEW use below, tagged distinctly (`household_income_source` ending `_qcew_wage_rate`) so it's never mistaken for a real ACS-rate estimate. This tier does carry the per-job-vs-per-household mismatch caveat the ACS-rate tier above it doesn't.
   - Both measures go through the same anchor-and-interpolate step: each year's figure (real or estimated) is anchored at that year's midpoint (July 1) and linearly interpolated month-by-month against adjacent years' anchors — see Architecture notes — so the output is a genuine monthly series for each, not a flat per-year value. Writes `outputs/income_combined.csv` (`fips, year, month, income_est, income_source, household_income_est, household_income_source`).
6. **`create_output.py`** — reads each configured Zillow CSV (see step 4's `zillow_paths`) and `outputs/income_combined.csv`, melts each Zillow file's wide monthly columns to long form tagged with its `home_type`, stacks all home types together, and merges on `(fips, year, month)` — both sides are monthly now. Computes both `price_to_income_ratio` (per-capita) and `price_to_household_income_ratio`. Also joins ZORI rent onto every home_type's rows as a `zori` column and computes `rent_to_household_income_ratio` (`zori * 12 / household_income_est`, a share — 0.25 = 25%; household rather than per-capita income since rent is paid per household). Writes `outputs/fips_zillow_income.csv`, one row per county-month-home_type. Run with:
   ```
   python build_income.py && python create_output.py
   ```

Search the codebase for `# UPDATE:` comments — these mark the specific values/paths a user needs to edit before running (FRED key file, Zillow file path).

7. **`join_diagnostics.py`** — one-off report (not part of the regular pipeline, run manually) on how much data is lost joining Zillow ↔ FRED-derived income: names FRED reports that never matched a FIPS via the NRCS crosswalk, counties present in one source but not the other, and (fips, year, qtr) tuple-level coverage. Run it after changing `data/nrcs/nrcs_fips_codes.csv` or re-fetching FRED to check whether match rate improved. As of the last pass: 3,056 of 3,071 Zillow counties matched (99.5%) — remaining gaps are ~15 Virginia jurisdictions (Fairfax County among them) that have no FRED per-capita income entry under any name, a genuine gap in FRED's own release-175 table, not a crosswalk problem.

## Web visualization (`web/`)

A single-page vanilla JS + D3 app (no build step, no framework) — national choropleth with a bottom timeline slider, click a county to drill into its state (county list on the left), click a county there to open a detail inset with dual-line home-value/income charts. Hash-based routing (`#/state/<fips>/<monthIndex>/county/<fips>`) rather than History API pushState, specifically because **this is meant to be deployed as a static site to S3 behind CloudFront** — hash routing needs no server-side/CloudFront rewrite rules for deep links to work, unlike pushState routing which would need a custom-error-response-to-index.html rule.

- **`web_data_build.py`** — reads each configured Zillow CSV (same `zillow_paths` dict as `create_output.py`, kept separate since the two scripts run independently) and `outputs/income_combined.csv`, and writes `web/data/dataset.json`: counties, months, a counties×months `income` matrix (per-capita, already interpolated monthly by `build_income.py`, so the client does no year-level logic at all), a parallel `householdIncome` matrix (median household income, same shape), and `zhvi` — now `{home_type: counties×months matrix}` (one matrix per configured Zillow home-value series, e.g. `all_homes`/`single_family`, same shape as `income`) rather than a single matrix, so the client has the data to switch between home-value series — plus `rent` (counties×months ZORI matrix, null where uncovered; omitted entirely if `zillow_rent_path` is `None`, in which case the client drops its rent metric buttons), `incomeEstimatedYears`/`householdIncomeEstimatedYears` (`{fips: [year, ...]}`, for flagging the QCEW-rate-/SAIPE-growth-rate-estimated portion of a county's income line, respectively) and a copy of `data/geo/counties-10m.json`. `web/app.js` reads `data.zhvi[state.housing]` (see the three-selections entry below for the `housing-toggle` UI that sets it) rather than treating `zhvi` as a single matrix. Run this script after `build_income.py`/`create_output.py`. `web/data/*.json` is gitignored (regenerated, like `outputs/*`) — run this script before serving `web/` locally or deploying it. Shipping income as a full matrix (rather than one value per year) roughly doubles `dataset.json`'s size, and shipping multiple `zhvi` home_type matrices multiplies that further (~12MB uncompressed per matrix as of this writing) - an accepted tradeoff for a genuinely smooth income line/ratio and switchable home-value series instead of a stepped/single one. The `householdIncome` matrix adds roughly one more `income`-sized matrix on top of that.
- **`web/vendor/`** — D3 v7 and topojson-client, vendored (downloaded, not loaded from a CDN at runtime) so the deployed static site has no external runtime dependency.
- **`web/app.js`** is a single file; state lives in one `state` object (`view`, `stateFips`, `countyFips`, `monthIndex`), hash ↔ state is synced both ways (`applyHash`/`pushHash`), and there's one `render()` entry point that redraws whatever's visible. Kept intentionally simple/flat rather than componentized, matching this repo's existing "don't over-engineer" style.
- **Three selections drive the UI:** the map-legend box has three labeled button groups — **Housing** (`housing-toggle`: All homes / Single-family / Rent → `state.housing`, a `data.zhvi` key or `"rent"`), **Income** (`income-toggle`: Per-capita / Household → `state.incomeBasis`), and **Map shows** (`metric-toggle`: Housing / Income / Ratio → `state.metric`). The ratio is always the selected housing measure ÷ the selected income measure: a multiple (e.g. 4.2x) for home values, or annual rent as a share of income (e.g. 23%) for rent (`ratioAt()`). Values for the current selections come from `housingAt`/`incomeAt`/`ratioAt`, and labels/formatting from `housingLabel`/`incomeLabel`/`ratioLabel`/`fmtHousing`/`fmtRatio`, so legend, tooltips, and overview never disagree. All three setters share `refreshSelection()` (legend, map colors, county-list graying, overview, county detail charts) — no geometry rebuild. Housing buttons for anything `dataset.json` doesn't carry (an unconfigured home_type, or rent) are removed at boot. A **Color scale** group (National / This state) appears alongside in state view.
- **Overview shows only the current selections:** a coverage card (counties with data this month for each of housing / income / ratio — they differ a lot, since ZORI covers far fewer counties than ZHVI and income lags the latest months) plus one highest/lowest/average card each for the selected housing measure, income measure, and ratio. The county detail inset follows the same selections: three stacked mini-charts — selected housing measure, selected income measure (with its growth-rate-estimated tail drawn faint), and their ratio — redrawn by `refreshSelection()`; a county with no data for the selected housing measure (common for rent) says so in that chart's title.
- **Color scale:** ratio's scale is fixed (`isFixedScaleMetric()`, not month-relative) — computed once from a 2nd/98th-percentile sample across all counties/months, so a color means the same ratio at any point on the timeline, not a re-normalized "this month's relative spread." Housing (home value or rent) and income are nominal dollar figures that trend up over the ~25yr range (appreciation/inflation), so a scale fixed like ratio's would leave early months uniformly dim and late months uniformly bright — those instead get a scale recalculated per month (`getMonthColorScale()`, cached by metric/selection/scope/month), sampled from just that month's values.
- **Default month on load** is the latest month with *any* income coverage, not Zillow's own latest month — FRED's annual income lags Zillow's monthly data by a year or more, so defaulting to Zillow's latest month would show an all-gray "no data" map on first load. See `latestMonthWithIncomeData()`.
- Counties/list entries with no income data for the selected month render gray / grayed-out text (per-month, not just per-county — a county can have data for some months and not others depending on FRED's coverage).
- Deploying: `web/` is the entire deployable unit. `scripts/deploy.sh` syncs it to `s3://$BUCKET/housing/` and invalidates that path on the shared CloudFront distribution — same S3 bucket + distribution as the peer `sun_overlay` and `cu_salary` projects, each under its own path prefix (`housing`, `sun`, `cu`). Copy `scripts/deploy.env.example` to `scripts/deploy.env` (gitignored) and fill in `BUCKET`/`CLOUDFRONT_DISTRIBUTION_ID` before running it. Run the full build pipeline first — `deploy.sh` refuses to run if `web/data/dataset.json` is missing/stale.
- **Attribution:** the map has a "Data sources" box (bottom-right of `#map-panel`) linking to Zillow, FRED/BEA, BLS QCEW, FRED/Census SAIPE, and us-atlas/Census TIGER — required/expected attribution for each (Zillow's terms ask for "Data Provided by Zillow Group" cited on every page displaying their data; FRED asks both the source agency and FRED be cited). Update this if a data source changes. The same box has a **Notes & caveats** list (mean vs. median income, ZHVI/ZORI definitions, rent ratio's all-households denominator, monthly interpolation, estimated recent years, nominal dollars, coverage gaps such as Connecticut's post-2022 planning-region switch) - keep it in sync when the pipeline's methodology or coverage changes.

## QCEW: growth-rate source now, parked as a level/income source

BLS's Quarterly Census of Employment and Wages was originally tried as a *quarterly, sub-annual* replacement income source (splicing QCEW wage levels directly in alongside FRED's) — that's parked (see below), the active pipeline is FRED-only for actual income *levels*. It's now used for a narrower purpose: `build_income.py`'s extrapolation step uses QCEW's real average-weekly-wage year-over-year change as a growth *rate* to project FRED's last known figure forward into years FRED hasn't published yet. That distinction matters: a rate transfer doesn't inherit the units mismatch that splicing levels would (see Caveat below).

If sub-annual *income-level* granularity is needed again (the original, larger idea):

- **`qcew_fetch.py`** already fetches it: `https://data.bls.gov/cew/data/api/{year}/{qtr}/industry/10.csv` (industry code 10 = total all industries), one CSV per year/quarter covering every county nationwide in one request, filtered to `own_code == 0` (total covered) and `agglvl_code == 70` (county-level total). Coverage is **2014 Q1 onward only** — confirmed directly against the API; earlier years 404 (BLS's *bulk downloadable* QCEW files go back further, but that's a different, unparsed format). `--start-year`/`--end-year`/`--limit` flags exist for bounded test runs. Output already sits in `data/qcew/` (gitignored — see Fetch policy note below on why data.bls.gov was used despite its robots.txt).
- **`data/qcew/LICENSE.txt`** has BLS's public-domain/attribution policy, saved for citing alongside a map/chart.
- To wire it back in: `build_income.py` would need a QCEW branch (annualize `avg_wkly_wage * 52`, tag `income_source = "qcew_wage_annualized"`) merged alongside the FRED branch, splitting on year (FRED for pre-2014, QCEW for 2014+). This was implemented once already — check git history around the QCEW integration commits for the working version to resurrect rather than rewriting from scratch.
- **Caveat if resurrected:** QCEW's average weekly wage (per covered job) and FRED's per-capita personal income (per resident, all income types) are not the same measure — splicing them creates a real methodology break at the 2014 boundary, not just a data-source swap. Keep an `income_source` column in the output so this is visible/filterable rather than papered over.
- **robots.txt note:** `data.bls.gov` (all paths) and `api.bls.gov` both declare a blanket `Disallow: /`, and `www.bls.gov` actively blocks plain automated requests. FRED (`api.stlouisfed.org`, robots-compliant) mirrors some BLS QCEW series but only at MSA/metro granularity, not per-county — so there's no fully robots.txt-compliant path to county-level QCEW data. Using `data.bls.gov`'s documented Open Data API anyway (treating the disallow as aimed at crawlers, not this documented third-party API) was a deliberate, explicit call — re-confirm that judgment call still holds before reviving this path.

## Fetch policy

Any code that fetches from an external API in this repo (FRED, BLS QCEW, Zillow, or any future source) must:
- Rate-limit to **no more than 1 request per second** as a ceiling — go slower still (e.g. FRED's 2s) if the source's own robots.txt/crawl-delay asks for it — and never issue requests in parallel/concurrently, always a serial loop with a delay between requests.
- Check for and rigorously respect that source's `robots.txt` and any documented rate-limit/usage policy or terms of service before adding or changing a fetch loop.
- Skip re-fetching data already saved to disk (as `qcew_fetch.py` and `fred_fetch.py` already do) rather than re-requesting it, to keep total request volume to a minimum — except when deliberately re-checking a previously-blank/unpublished period (`--force`).

This applies to scripts you write as well as one-off fetches you run yourself (e.g. via `curl`/`WebFetch`) while exploring an API's format.

## Architecture notes

- **FIPS is the join key on the Zillow side, no hand-built crosswalk needed there.** Zillow's county files carry `StateCodeFIPS`/`MunicipalCodeFIPS` directly. FRED's per-capita release has no FIPS of its own, so `build_income.py` attaches it via `data/nrcs/nrcs_fips_codes.csv`, matched on state abbreviation + county name (not the `data/zfmap/` crosswalk the legacy single-script pipeline used — that crosswalk bridged FRED names directly to Zillow names; going through FIPS instead is more direct and doesn't require Zillow-specific name matching). This name-match is imperfect for a handful of counties (e.g. FRED's "... Borough" vs. this crosswalk's "... County" for some Alaska boroughs) — a pre-existing gap, not new. SAIPE household income has no equivalent problem: its FRED series id embeds the FIPS directly (see step 2 above), so `build_income.py`'s household branch reads FIPS straight from the `data/fred_household/*.json` filenames, no name-matching at all.
- **Annual → monthly interpolation, not a flat broadcast:** both income sources publish once a year. Broadcasting that flat across all 12 months produces a visible step function - both in a per-county chart and at the choropleth's yearly color transitions - so `build_income.py` instead anchors each year's figure at its midpoint (July 1) and uses `numpy.interp` per county to linearly interpolate between consecutive years' anchors (including the QCEW-/SAIPE-growth-rate-estimated years, which become anchors too), holding flat before the first anchor / after the last (no invented trend beyond the known range) — the same `interpolate_monthly()` helper does this for both the per-capita and household series. Each interpolated month is tagged with its *nearest* anchor's source column, so the real/estimated distinction survives at roughly year granularity even though the values themselves are now smooth. `create_output.py` then merges Zillow and income directly on `(fips, year, month)`.
- **Recency gap:** BEA's county personal income release and Census's SAIPE release both lag roughly a year, so the most recent 1-2 years are often blank in a freshly-fetched file until published — re-run `fred_fetch.py --force`/`fred_household_fetch.py --force` on just the recent years periodically to pick up newly-published data (see Pipeline steps 1-2). Years past each source's own coverage are extrapolated from a growth rate (QCEW for per-capita, the release-249 household-income series for household — see step 5) rather than left blank; if the real figure is later published for one of those years, re-running the relevant fetch script with `--force` and rebuilding will replace the estimate with the real value (real rows always take priority — each extrapolation loop only fills years with no real entry for any county).
- **Output shape:** the output is long/tidy (one row per county-month with `price_to_income_ratio`/`price_to_household_income_ratio` columns and `income_source`/`household_income_source` columns), not the old wide format (one row per county with `ratio-<month>` columns per date).
- `data/zillow/*`, `outputs/*`, `data/fred/*.json`, `data/fred_household/*.json`, `data/fred_household_growth/*.json`, `data/qcew/qcew_*.csv`, and `fred_key.txt` are gitignored — none of these are checked in; they're either regenerated by the fetch/build scripts or (Zillow) must be downloaded manually per Pipeline step 4. `data/qcew/LICENSE.txt` is the one tracked exception in `data/qcew/`.
